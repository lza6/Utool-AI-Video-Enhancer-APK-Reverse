# 05 · 逆向方法论与踩坑记录

本项目在 **无 jadx 可用** 的前提下完成，方法是"自研扫描器 + 反汇编 + 线上探针"三件套。记录如下，供同类 App（Unity/RN/Flutter 之外的纯原生 + 强混淆）复用。

## 1. jadx 在本机永久卡死（最重要的坑）

现象：

```
INFO - Loaded classes: 13143, methods: 52168, instructions: 2344474
INFO - Resetting disk code cache, base dir: ...\skylot\jadx\cache\projects\...\code
（然后永远不产出，jadx_out 为空，进程 CPU 空转）
```

已尝试且**全部无效**：

- `--no-res` / `--no-debug-info` / `--show-bad-code`
- `-Xmx4g` → `-Xmx8g`（机器 41 GB / 空闲 12 GB，排除 OOM）
- 删除 `AppData\Local\skylot\jadx\cache` 全部内容
- `LOCALAPPDATA=D:\jadxcache` 重定向
- 单 dex（`classes.dex` 9.9 MB）单独反编译
- `--single-class v60.b`
- 清理 51 个残留 `Temp\jadx-instance-*`（其中一个 134 MB）

**替代方案**：`pip install androguard`（4.1.4），用 `AnalyzeDex` 逐 dex 加载，`get_source()` 反编译。


## 3. 没有 jadx 时怎么定位关键类

写了 5 个零依赖 DEX 扫描器（`src/tools/`）：

| 工具 | 能力 | 实现要点 |
|---|---|---|
| `dexref.py` | 找"引用了某字符串"的 类→方法 | 解析 header → string_ids → class_def → class_data(uleb128) → code_item，在指令区间里找 `1a AA BBBB` / `1b AA iiiiiiii` |
| `typeref.py` | 找"引用了某类型"的 类→方法 | 同上，但匹配 `const-class(0x1c) / new-instance(0x22) / check-cast(0x1f) / invoke-*(0x6e..)` 后的 type_idx |
| `pkgstr.py` | 按包前缀导出全部 const-string | 逐类聚合，过滤非可打印 |
| `mstr.py` | 按方法导出 const-string（带指令偏移） | 便于判断键值对顺序 |
| `xrefs.py` | ARM64 ELF 的 `ADRP+ADD` 字符串交叉引用 | capstone 解码，跟踪 adrp 目标页寄存器，遇 `bl/blr/b/ret` 清空 |

### 两个必须记住的编码细节

1. **`const-string` 的字符串索引在指令第 2 个 16 位单元**（`1a AA BBBB`），所以匹配 index 时应找 `pos % 2 == 0 and chunk[pos-2] == 0x1a`；写成 `pos % 2 == 1` 会全军覆没。
2. 字符串索引超过 `0xFFFF` 时只能是 `const-string/jumbo`，`struct.pack('<H', idx)` 会直接抛 `struct.error` —— 必须分流处理。

## 4. 导出符号走 PLT（第二个大坑）

`aes_key_setup` / `AES_CBC_PKCS7_Encrypt` 这类**导出**符号，在 PIC 编译的 .so 内部调用会走 PLT，因此：

- 在 `.text` 里扫 `BL <target>` **一个都找不到**；
- 正确方式：解 `.rela.plt`，按 `stub = 0x21c90 + (got_slot - 0x265d8)/8*0x10` 建表。
- 判断依据：`.plt` 段存在且 GOT 槽位有对应符号，就说明它是走 PLT 调用的。

## 5. `.data.rel.ro` 全 0（第三个坑）

指针表在 `.data.rel.ro` 里是 `R_AARCH64_RELATIVE` 重定位，**文件内容全 0**，实际值在 `.rela.dyn` 的 `r_addend`。
不解析 `.rela.dyn` 就永远看不到 JNINativeMethod 表。

## 6. 线上探针：把"错误码"当 schema

服务端返回**可读中文错误**，且多语言白名单式校验，非常适合逐字段探测：

```python
# 依次补字段，看错误码迁移
{}                                  -> -10001 packageName
{"packageName":PKG}                 -> -10002 uuid
{"packageName":PKG,"uuid":U}        -> -10003 accountId
{"...","accountId":X}               -> -10011 accountToken
{"..."}                             -> 0 success
```

另一个探针是 **404 明文 / 命中密文**：

```bash
# 未命中：明文 Spring 错误
{"timestamp":"...","status":404,"error":"Not Found","path":"/api/ai2/task/create"}
# 命中：base64 密文
U4lXt1TANIhd8Nh5mZb6e3wUatN8+I2QjjV0dsJ/...
```

用它一次性枚举出了 `{video,art,cutout,enhance,gen}/task/{create,query}` 全部命中
—— 后来发现中间段其实是 `modelType`，属于"能命中但语义错"的假信号，需要反编译才能校正。

## 7. 其它环境坑

- Windows 下**没有 `strings` 命令** → 用自写 DEX/ELF 扫描器或 Python 正则。
- Git Bash 会把以 `/` 开头的参数当路径转换（`/api/iap3/...` → `C:/Program Files/Git/api/...`）→ 加 `MSYS_NO_PATHCONV=1`。
- `com.tencent.mars` 只带 `libmarsxlog.so`（日志），不是网络库，别被误导。
- `libsigner.so` 是 **Adjust SDK** 的签名库，与业务加密无关。
- `bin.mt.signature` / `libelamods.so` 是 Mod 作者的注入物（MT 签名伪造 + native_jvm hook），与原厂协议无关。
